# Flutter patient-health prototype

- Open this directory as the Flutter project. The Android and iOS projects under `Devin/Natives` are independent; do not modify them as part of Flutter work.
- Flutter 3.47.2 / Dart 3.13.2 were used for initial development. Run `flutter doctor -v` and use an installed Flutter stable SDK compatible with `pubspec.yaml`.
- Main entry point: `lib/main.dart`, which launches `PatientHealthApp` within a Riverpod `ProviderScope`. Routes are in `lib/app.dart`; domain validation/conversions are in `lib/domain`; encrypted SQLite storage and platform key storage are in `lib/data`.
- Dependencies are pinned in `pubspec.yaml`; retain `pubspec.lock`. Riverpod manages data state and injection; go_router handles navigation; fl_chart provides interactive charts. Payload serialization is explicit and versioned rather than generated.
- Format and analyze: `dart format lib test integration_test` and `flutter analyze`.
- Unit/widget tests and coverage: `flutter test --coverage`. Coverage output: `coverage/lcov.info`.
- Device integration: `flutter test integration_test/app_test.dart -d <device-id> --no-uninstall`. Use a dedicated test emulator/simulator. Integration fixtures use a separate, uniquely named SQLite database and do not delete/reset production records or platform keys. The default Flutter integration command otherwise uninstalls the app afterward; never run it against an installation containing data you need to keep.
- Android debug build: `flutter build apk --debug`. Android minimum API: 26; compile/target API: 36. Flutter uses its configured Android Studio/JDK toolchain; do not change global Flutter/JDK settings to work around failures.
- Run: `flutter run -d <device-id>`. The normal entry point must be rebuilt after integration tests; their installed APK/app runs the test harness, not the normal app.
- iOS deployment target: 17.0. Bundle ID: `com.example.patientHealthFlutter`; Android app ID: `com.example.patient_health`, distinct from the native apps. Choose your own developer team before physical-device distribution. Do not disable simulator code signing: platform Keychain access must remain functional.
- `flutter_secure_storage` 9.2.4 uses CocoaPods fallback on iOS because that pinned plugin does not support Swift Package Manager. The installed CocoaPods toolchain is required.
- Patient payloads use AES-256-GCM before SQLite storage, with UUIDs authenticated as associated data. A random key is held in Android Keystore-backed encrypted preferences or iOS Keychain (`unlocked_this_device`). Missing/corrupt keys or unsupported payload versions fail closed; never silently reset records or introduce destructive migration fallbacks.
- Android backup/device transfer is disabled, and the activity uses `FLAG_SECURE`. Do not disable screenshot protection for previews. The Flutter privacy overlay hides content when inactive; it is not authentication, biometric locking, or iOS screenshot prevention. iOS backup exclusion, recovery, and migration policies require further work; device-only keys are not restored to a new device.
- Drafts live only in widget memory and are not stored in plaintext restoration bundles. Unsaved drafts are lost on process termination. DOB must be explicitly selected; examination choices match both native apps. Unit changes clear the affected input rather than silently reinterpret it.
- Only synthetic data is permitted. Medical ranges are illustrative adult values, not clinical decision support. There is no live backend/FHIR API, authentication/roles, formal consent history, audit trail, CSV/PDF export, background sync, localization, or production compliance certification. Dev/QA/Prod flavors and production release signing remain pending; the generated Android release template is not ready for distribution.
- `requirements.md` and `todo.md` are read-only specifications. Do not mark requirements complete without explicit permission and verification. Never log patient payloads, keys, or unexpected exception details.
